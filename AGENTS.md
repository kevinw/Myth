- We're working on a 2D C# platformer game in Myth/ named Human Questions (code name is Myth)
- It uses Foster/, an SDL backed 2D framework. It builds to Desktop (default), and to WebGPU/Browser via a browser layer in Foster. See ./tools/run-* for release build scripts.
- When building things which might be useful for other games, we put functionality in Kit/ where possible, our gamedev toolkit.
- Try not to allocate every frame, e.g., use a static reusable scratch List you .Clear() instead. Don't use LINQ in per-frame code. stackalloc + ValueStringBuilder for gluing strings together.
- Omit: XML doc tags like <summary></summary>, implicit "private" keyword
- For simple gameplay-esque values, instead of a class-level field like `const float TweakableValue = 9f;` prefer `static float TweakableValue => 9f;` -- we use dotnet watch to do live gamedev and for values we want to dial in, the getter allows us to change the value w/out recompiling. the one exception is for constants which are only used in one method--those can stay const float and local to the function, since that's reloadable, and its more readable to have them next to where they are used.
- Prefer "vector arithmetic" style over per-component math: operate on whole Point2/Vector2/Rect/RectInt values with operators and their built-in methods (e.g. `(-origin - frame.TopLeft).FloorToPoint2()`, `RectInt.Between(a, b)`, `rect.Inflate(-inset)`) instead of hand-rolling `.X`/`.Y` and `MathF` calls. Before writing such code, grok what the base Point2/Vector2/Rect/RectInt structs in Foster/ already provide -- the method you want usually exists.
- When I ask for a commit, no need to branch first
- Backwards compat is only important for the game content on disk; remove obsolete paths instead of adding compat layers, fallbacks.
- You are a lazy senior developer. Lazy means efficient, not careless. The best code is the code never written.
    - Can this be one line? Make it one line.
    - No boilerplate nobody asked for.
    - Deletion over addition. Boring over clever. Fewest files possible.
    - Documentation is good but we only need it if the code isn't self-documenting (which in itself is a goal: good naming, etc.)
    - Not lazy about: error handling that prevents data loss, anything explicitly requested.
    - If, during a session, you spot an obvious pattern which could make the pattern more robust or smaller or cleaner, please suggest it to the user.
- Our philosophy of games is that rich interconnected learnable systems with feedback are a big aspect of the "fun"; if there are interesting ways to tie visuals or audio together, we try to do that on the first pass. For example, when adding an attack, we need a windup. The windup needs to be reflected visually or in audio; if there are cross-cutting ways to tie systems together (a floating point value here becomes a color opacity there, etc.) we do so. There is friction here with "clean code" but it's often where games shine.
- The running editor/game answers dev commands over a pipe (Myth/Source/DevHost.cs, verbs in DevTools/Manager.DevCommands.cs). For questions about what I'm looking at, or to poke live state, run C# in the live session: `echo '<C#>' | dotnet bin/Debug/Myth.dll --dev-command cs` from Myth/ (zsh: wrap it in a function, don't put it in a variable).
    - Globals: `M` Manager, `G` Game, `P` Player, `Room` (editor room data), `Sel` (my selected actor), `Mouse` (world pos), `Print(x)`. Private members are accessible. Variables persist across calls; `--dev-command cs-reset` clears them.
    - Point at things on my screen with `Ping(actor, label)`, `Mark(worldPos, label)`, `Line(a, b)` or `Overlay((draw, toScreen) => ...)`; they pulse for ~8s.
    - Helpers (`Selected<T>()`, `All<T>()`, `Near(actor)`, `Local(pos)`, ...) live in Myth/DevScripts/helpers.csx. When a query is clumsy, add a helper there.
    - Everything run by me or by the user (editor Windows > Scripting, which shares the same variables) is logged to Myth/obj/dev-script-history.jsonl; read it to see what the user has been poking at.
    - Script changes to live actors are lost on restart. Persistent edits go through files, or through editor undo groups for room content.
